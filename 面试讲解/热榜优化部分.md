## 热榜优化

### 背景

首页热榜根据文章的点赞、收藏、评论和浏览行为计算热度，展示 Top5。由于该功能位于首页，属于高频读场景。

### 初始方案

初始方案直接在 MySQL 中根据多个互动字段计算热度，并通过 `ORDER BY` 排序获取 Top5。

在数据量较小、读并发较低时可以正常工作；但数据量增长后，每次请求都需要对大量候选文章执行热度计算和排序。

### 问题发现

压测环境：

- 服务器：2 核
- 数据量：20 万篇文章
- 并发：300 并发读取热榜接口
- 现象：主机 CPU 接近 200%，MySQL 容器 CPU 峰值约 170%

通过 EXPLAIN 执行计划进一步定位，发现问题不在普通过滤条件，而在动态热度表达式排序。`status`、`hidden` 等字段可以建立索引，但热度由浏览、点赞、收藏、评论等多个字段共同计算，普通索引无法直接服务该 `ORDER BY`。

因此在高并发下，每个热榜请求都在重复执行"扫描候选文章、计算热度、排序、获取 Top5"，MySQL 成为性能瓶颈。

### 替代方案思考

如果不使用 Redis，我会采用 MySQL 热榜快照表方案：后台定时任务周期性计算热度并写入 Top N 快照，首页只读取预计算的 Top5。

该方案通过分钟级最终一致性降低高并发读压力，但定时重算仍会消耗 MySQL 资源，且互动后榜单不能立即更新，因此最终没有采用。

### 最终方案：Redis ZSet 实时日榜

核心思想是将热榜从"读时计算排序"改为"写时增量维护排序"。

```text
点赞 / 收藏 / 评论 / 有效浏览
        ↓
MySQL：持久化业务事实
        ↓
Redis ZSet：原子更新当天热度分
        ↓
首页：本地缓存 → Redis Top5 → MySQL 批量补齐展示信息
```

Redis 按内容类型和日期维护日榜：

```text
content_hot_rank:daily:article:20260913
```

其中：
- member：文章 ID
- score：文章当天累计热度分

互动成功后，通过 ZINCRBY 原子更新对应文章的分数：

```go
// 点赞/收藏：+2；评论：+3；有效浏览：+1。
// 取消操作或删除评论时传入负分。
newScore, err := rdb.ZIncrBy(ctx, dailyRankKey, delta, articleID).Result()

// 分数归零后移出日榜。
if newScore <= 0 {
    _ = rdb.ZRem(ctx, dailyRankKey, articleID).Err()
}
```

读取时通过 ZREVRANGE 直接获取 Top5 文章 ID 和分数，再使用 `WHERE id IN (...)` 批量查询文章标题和可见状态，并按 ZSet 的排名顺序组装响应。

首页 Top5 增加 10 秒本地缓存。缓存命中时不访问 Redis 或 MySQL；缓存失效时，使用 Singleflight 合并同一榜单的并发回源请求，同一失效周期只有一个请求重建缓存，其余请求共享结果。

### 一致性与降级

MySQL 是文章、点赞、收藏、评论等业务事实的持久化数据源；Redis ZSet 只是实时排序索引。

Redis 更新在 MySQL 主业务成功后执行。Redis 短暂异常不会导致点赞、评论失败，但榜单可能存在短暂延迟。

文章删除、隐藏或转草稿时，主动使用 ZREM 将文章从当天日榜移除；读取榜单时还会再次校验文章是否已发布且可见，避免脏数据展示，并惰性清理失效成员。

浏览量通过 SETNX 做当天去重：同一登录用户对同一内容当天只计一次分；游客和作者本人浏览不参与榜单计分。

每天通过切换日期 Key 实现日榜重置。当天只读写当天 Key；旧日榜保留约 31 天后通过 TTL 自动清理。这里"保留 31 天"是保留历史日榜，并不是将 31 天积分累计成月榜。

### 压测结果

- 并发：300
- QPS：1501 → 2783
- P95：294ms → 133ms
- 同一缓存失效周期：仅触发 1 次缓存重建

### 面试讲解话术

最初热榜由 MySQL 在查询时根据浏览、点赞、收藏和评论等字段计算热度，再排序取 Top5。数据量较小时没有明显问题，但在 20 万文章、300 并发压测下，2 核机器 CPU 接近打满，MySQL 容器 CPU 峰值约 170%。

我通过 EXPLAIN 执行计划确认，问题在于热度是多字段动态表达式，普通索引无法直接优化排序；每个请求都要重复扫描候选文章、计算热度并排序。

因此我将方案改为 Redis ZSet。互动发生后，先由 MySQL 持久化点赞、评论等业务事实；成功后使用 Redis ZINCRBY 增量更新该文章当天的热度分。查询时通过 ZREVRANGE 直接取 Top5，不再让 MySQL 计算和排序全量文章。

首页 Top5 访问频繁，我又增加了 10 秒本地缓存，减少 Redis 和 MySQL 回源。为避免缓存过期瞬间大量请求一起穿透，使用 Singleflight 合并同一个榜单的并发重建请求，一个请求回源，其余请求共享结果。最终在 300 并发下，QPS 从 1501 提升到 2783，P95 从 294ms 降到 133ms。

### 面试官可能追问

**2. 为什么选择 Redis ZSet？**

ZSet 天然支持"member 对应 score 并按 score 排序"。互动时使用 ZINCRBY 原子加减分，查询时使用 ZREVRANGE 直接获取 TopN。它适合实时排行榜，避免 MySQL 每次查询都重新计算和排序。

**3. 一次点赞会更新很多文章吗？**

不会。一次点赞只更新当前文章的一个 ZSet member。

```text
ZINCRBY daily_rank_key +2 articleID
```

Redis 的价值不是一次更新很多内容，而是用内存中的有序集合维护实时排名，避免高频查询时由 MySQL 重复排序。

**4. 为什么 MySQL 和 Redis 都要写？**

MySQL 保存点赞、评论等业务事实，是数据源；Redis 保存实时排名，是可重建的排序索引。

MySQL 保证业务正确性，Redis 保证热榜读取性能。Redis 更新失败不会让点赞失败，只会导致榜单短暂延迟。

**5. 浏览量如何防刷？**

使用 SETNX 创建"用户-文章-日期"的去重 Key。只有首次创建成功才给文章加分；同一用户当天重复刷新页面时，Key 已存在，不再加分。游客和作者本人浏览也不计入榜单。

**6. 热门文章被删除或隐藏怎么办？**

删除、隐藏、转草稿时主动执行 ZREM 撤出榜单。读取时还会从 MySQL 校验文章状态；即使 Redis 删除失败，已删除或隐藏文章也不会返回给用户，并会在读取时被惰性清理。

**7. Redis 网络故障怎么办？**

首页 Top5 的本地缓存未过期时，优先返回旧榜单；本地缓存也失效时，热榜降级为空，不影响点赞、评论、发文等核心业务。

Redis 是排序索引，不是业务事实数据源。若 Redis 全量丢失，可基于 MySQL 的当天互动数据异步重建当天 ZSet。

**8. 日榜如何每天清零？为什么旧 Key 保留 31 天？**

每天使用新的日期 Key，例如今天写 `...:20260913`，明天写 `...:20260914`，所以积分天然按天隔离，不需要零点扫描全量文章清分。

旧 Key 保留 31 天是为了历史排查和自动清理；首页始终只读取当天 Key。若需要月榜，应单独设计月榜 Key，不能直接把多个日榜 Key 当作月榜。

**9. 本地缓存会不会导致榜单不实时？**

会，首页 Top5 最多可能有 10 秒延迟。这是一个明确取舍：首页高频访问场景下，用短暂最终一致性换取更低延迟和更少的 Redis/MySQL 压力。

**10. Singleflight 能解决跨实例缓存击穿吗？**

不能。Singleflight 只在单个 Go 进程内合并请求。多实例部署时，每个实例最多各有一个请求回源；如果规模继续扩大，可以进一步使用分布式锁、逻辑过期异步刷新或预热策略。



**12. Redis 内存会不会爆？ZSet 无限增长怎么办？**

不会无限增长。每天切换新的日期 Key，当天只写当天的 Key；旧 Key 通过 TTL 31 天自动清理。单个日榜 Key 的 member 数量上限是当天有互动的文章数，不是全量文章数。同时互动后分数归零的文章会被 ZRem 移出，进一步控制大小。

**13. 上线时老数据怎么迁移？热榜从 0 开始吗？**

上线当天会触发一个初始化任务，扫描当天已有的互动数据，批量计算热度分并写入当天的 ZSet。这样热榜从上线那一刻起就有数据，不需要从零积累。历史互动（非当天）不参与日榜，符合"日榜只看当天互动"的设计。

**14. 月榜或周榜怎么做？**

如果要支持周榜或月榜，需要单独设计 Key，例如 `content_hot_rank:weekly:article:2026W37`。周榜/月榜通过定时任务每天汇总当天日榜分数增量累加到周榜 Key，而不是把多个日榜 Key 直接合并。这样查询性能和日榜一样是 O(logN)，且日榜逻辑不受影响。

**15. 点赞写入 MySQL 成功但 Redis 写入失败怎么办？**

这是典型的分布式一致性问题。核心原则是：MySQL 是数据源，Redis 是可重建的排序索引，索引丢了可以重建，业务数据不能丢。

处理策略是**重试 + 异步对账**：

1. Redis 写入失败后立即重试 2~3 次（网络抖动通常重试即可恢复）
2. 重试仍失败则记录失败日志，不影响点赞成功返回（业务优先）
3. 后台定时对账任务：每隔几分钟扫描当天互动记录，对比 MySQL 中的实际互动数与 Redis 中的 score，发现偏差则修正 ZSet

同时首页 Top5 有 10 秒本地缓存，能掩盖短暂的不一致窗口，用户几乎感知不到。

### Singleflight、互斥锁、分布式锁对比

| 维度 | Singleflight | 互斥锁（Mutex） | 分布式锁（Redis SETNX） |
|------|-------------|----------------|----------------------|
| **目的** | 合并相同 key 的并发请求，避免重复回源 | 保证同一时刻只有一个 goroutine 执行 | 保证同一时刻只有一个实例执行 |
| **作用范围** | 单进程内 | 单进程内 | 跨实例，全局生效 |
| **并发行为** | 第一个请求执行，其余**等待并共享结果** | 拿到锁的执行，其余**阻塞等待** | 拿到锁的执行，其余**等待或降级** |
| **结果共享** | 是——所有等待方拿到同一个结果 | 否——每个等待方重新获取锁后再执行 | 否——每个实例需独立获取锁 |
| **性能** | 高——N 个并发只执行 1 次 | 中——N 个并发串行执行 N 次（进程内） | 低——涉及网络往返，串行执行且有网络开销 |
| **适用场景** | 缓存击穿防护，相同查询合并 | 保护进程内共享资源 | 跨实例任务调度、防重复执行 |

**各自典型场景：**

- **Singleflight**：本地缓存失效时合并并发回源请求，单进程内用，零网络开销
- **Mutex**：Go 代码中保护某个 goroutine 内的共享变量，如计数器、状态机
- **分布式锁**：多个 Pod/实例部署时，确保定时对账任务、批量重建等操作只在一个实例上执行；Redis 缓存失效后多个实例同时检测到并重建时，锁保证只有一个实例去重建，其余实例等待结果后直接读取

**为什么热榜场景选 Singleflight？**

首页 Top5 有 10 秒本地缓存，缓存失效时可能有大量请求同时穿透到 Redis。Singleflight 在单进程内将这些相同请求合并为 1 次回源，零网络开销，效果最好。而 Mutex 仍然串行执行 N 次，分布式锁还多一次网络往返，都没有必要。

简单来说：**Mutex 是"进程内排队"，分布式锁是"跨实例排队"，Singleflight 是"来一个就行，其他的直接拿结果"。**
